# Database migrations (Alembic)

The schema is managed with Alembic (`backend/alembic/`). The database URL comes
from `DATABASE_URL`, the same variable the app uses.

```bash
cd backend
alembic upgrade head                       # apply migrations
alembic revision --autogenerate -m "what changed"   # after editing models
alembic check                              # fails if models and migrations drift
```

- The baseline (`0001`) is idempotent: tables that already exist are skipped, and
  the legacy `canonical_orders.customer_id` column is added if missing. It is safe
  on new databases and on ones created by the old startup `create_all()`.
- **Local development:** unchanged. The app still creates tables on startup.
- **Hosted deployments:** set `GUESTLIFT_AUTO_CREATE_SCHEMA=0` and run
  `alembic upgrade head` as a release step before starting the API.
- Always review autogenerated migrations; Alembic cannot detect everything
  (renames, data migrations).

## Revision 0002: workspace scoping of the demo tables

`canonical_orders`, `import_runs`, `campaigns`, `campaign_redemptions` and
`campaign_import_runs` now carry `workspace_id`. Uniqueness that used to be
global (one order per provider and id, one redemption id, one campaign id) is
now per workspace.

- Existing rows are backfilled into the `public-demo` workspace.
- The unauthenticated demo endpoints (behind `GUESTLIFT_ENABLE_DEMO_ENDPOINTS`)
  only ever read and write `public-demo`. Private merchant data lives in the
  tables keyed to `saas_workspaces`, which were already workspace-scoped.
- Local databases created before this revision are upgraded automatically on
  startup (when `GUESTLIFT_AUTO_CREATE_SCHEMA` is not `0`). Hosted deployments
  run `alembic upgrade head` as before.
- Tested against SQLite and PostgreSQL 16, including adoption of a populated
  database created by the old `create_all()` path.
- **Downgrade deletes rows belonging to any workspace other than
  `public-demo`**, because they could collide once global uniqueness returns.
  Take a backup first if that ever matters.

`tests/test_workspace_scoping.py` fails if a new table is added without a
`workspace_id` column and without an explicit exemption.
